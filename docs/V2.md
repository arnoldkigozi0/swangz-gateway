# Swangz AI Hub V2 — implementation map

V2 turns the gateway into the company's AI control plane: every important AI action should be
attributable — **who, what, for what, when, where, from which machine, under which authority, with which
account, at what cost, with what outcome** — and an administrator should be able to govern, investigate,
restrict, revoke and respond. This file is the working map: what existed when V2 started (schema v12,
Oct 9, 2026), what V2 adds, and what is still open. It describes the code as it is, not as hoped.

Status words: **Existing** (built and tested before V2) · **Partial** (some of it) · **Missing** ·
**Risky** (works, but has a known weakness) · **V2** (added in V2, tested) · **Open** (still not done).

## 4. Still open after V2

Nothing below is claimed as done.

- **Vendor reconciliation and actual costs.** No vendor usage or invoice import: costs are estimated
  (price table, media rates) or allocated (plans); "actual" never appears. Turns make matching a vendor's
  history to people possible; doing it automatically needs each vendor's admin API.
- **SCIM / vendor seat sync**, scheduled or emailed reports, WhatsApp alerts.
- **Audit log off the box.** Append-only through the gateway, but someone with a shell can still edit
  the database (see `docs/SECURITY.md`).
- **Purpose inference** is keyword rules — explainable and private, not clever. No model is asked, by
  design; the taxonomy and keywords need tuning on Swangz's real traffic.
- **Location** needs an admin to import an offline table (DB-IP Lite / IP2Location LITE) and refresh it
  monthly; none ships with the code.
- **Device fingerprinting** beyond one key per device and the user agent; platforms are often unknown.
- **Multi-tenancy**: one company per gateway.
- **Role-specific dashboards** (a billing home, a security home); roles change what can be changed, not
  what is shown first.
- **Browser matrix**: checked in headless Chromium at 1440, 1280, 1024, 768 and 390, dark and light,
  as owner and viewer (Oct 9). Not checked: real Safari / Firefox, screen readers end to end.

## 5. Manual provider-account registry (Amendment 01 task 1, schema v24 and v25)

A person tells Swangz which AI subscription they hold, and may add what they know about it. Every row is a
**declaration by the holder**: source `holder_declared`, `confirmed: false`. Nothing is fetched from a provider, and
nothing reads these tables to decide an entitlement, policy, turn, subscription, licence, spend figure, search result,
Timeline entry or notification. Code: `gateway/registry.py` (routes), `gateway/registry_schema.py` (v24, v25); tests
`tests/test_provider_registry.py`.

- **Tables.** `provider_accounts` (one per holder, tool and route; only ever ended, never edited or deleted) and
  `provider_account_values` (append-only; the latest row per kind is current). Triggers abort UPDATE/DELETE on values,
  DELETE on accounts, any account edit other than active→ended, and a value on an ended account. `INSERT OR REPLACE` /
  `REPLACE INTO` delete the row they replace without firing DELETE triggers (`recursive_triggers` is off and stays off), so
  BEFORE INSERT guards abort an insert whose id already exists and an account insert that would take the place of an
  active (holder, tool, route) row under a new id; `CHECK (id > 0)` keeps those guards exact. Foreign keys to
  people and tools are RESTRICT, so deleting a tool that has registry rows is a 409 `has_provider_accounts`. A partial
  unique index allows one active account per (holder, tool, route); an ended one may be registered again as a new row.
  Retention purges leave the registry alone. v24 is a **tuple** migration: each element is one statement, because a trigger
  body holds semicolons (older entries are strings and are still split on `;` exactly as before; there is no SQL parser). **v25 repairs v24's guards in place** (v24 is frozen; a pre-release database that already ran it has the weak ones). An explicit
  NULL in a defaulted column (`status`, `label`, `assertion`, `account_holder_kind`, `currency`) is seen by a BEFORE trigger as
  NULL, but `INSERT OR REPLACE` / `UPDATE OR REPLACE` then store the default, and `NULL = 'active'` is never true, so v24's
  guards let a NULL-status insert replace an active row and a NULL label or assertion edit a retained one. v25 drops the four
  weak triggers by name (`IF EXISTS`), then installs: accounts BEFORE INSERT and BEFORE UPDATE abort if any required field is
  NULL; `no_replace` treats a NULL status as active and compares holder/tool/route with `IS`; `only_end` compares every
  column with `IS` inside `NOT COALESCE(..., 0)`; values BEFORE INSERT abort on a NULL currency; `not_after_end` coalesces a
  missing account. Nothing is rebuilt, moved or deleted, and no pragma changes. The application already writes every column
  explicitly (a test traces its statements). Side effect: a second active company-held row for one tool and route (no route
  can write one) is now refused too, because `IS` matches NULL holders.
  The `api`/`enterprise`/`admin_declared` and company-holder values exist in
  the schema only; no route can write them.
- **Who may call.** Every route needs an ordinary active, approved web session. None is `paused_ok`; paused or ended
  people, extension sessions and device keys are refused, and writes need the `x-swangz-app` header. A person only
  ever reaches their own accounts (another person's id answers the same 404 as a missing one). 20 active accounts per
  person, 200 values per account, 20 writes and 120 reads a minute per person.

**Staff API** (`/api`; JSON, strict: an unknown field is 400 `unknown_field`; the holder is always the session):

| Call | Body | Answer |
|---|---|---|
| `GET /provider-accounts[?status=all\|active\|ended]` | | `{items, limits, routes, value_kinds, note}` |
| `POST /provider-accounts` | `{tool_id, route: individual\|seat, payer, label?}` — individual payer `person`\|`none`; seat payer `company` (may be omitted) | 201, the account |
| `GET /provider-accounts/<id>` | | the account plus `history` (every value, newest first) |
| `POST /provider-accounts/<id>/values` | `{kind, value, currency?, as_of?}` | 201, the account |
| `POST /provider-accounts/<id>/end` | `{}` | 200, the account (repeating it changes nothing) |

An account is `{id, tool_id, tool, route, payer, assertion: "holder_declared", confirmed: false, label, status, created,
ended, created_by, values}`. `values` has one entry per kind: `{state: "declared", id, value, currency?, as_of, recorded, source: "holder_declared",
confirmed: false}`, or `{state: "unavailable"}` when nothing was declared (never zero). Kinds: `plan` (text ≤60),
`quota_limit`, `quota_used` (decimals 0..1e12), `period_end` (date 2000..2100), `credit_balance`, `monthly_price`
(decimals; these two need a 3-letter ISO 4217 `currency`, and the others must not carry one). `as_of` is a date, at
most tomorrow, by the gateway's own calendar (`GATEWAY_TZ_OFFSET`, Kampala by default; not UTC). Amounts take at most six
decimal places, as numbers or text: more is refused, never rounded (`1e-7` is `bad_number`). Label ≤80 chars; text is
NFC-normalised and trimmed, refused if it holds any Unicode "other" character (controls, format characters such as bidi
marks and zero-width spaces or joiners, surrogates, private use, unassigned) or a line/paragraph separator, and refused
(without being repeated) if it starts with `sk-`, `AKIA`, `ghp_`, `xox` or `Bearer ` in any letter case, or holds a run of
32 key-like characters. Currency codes are SIX's ISO 4217 List One (published 2026-09-17; fetched 2026-11-06 from
`https://www.six-group.com/dam/download/financial-information/data-center/iso-currrency/lists/list-one.xml`, sha256
`33139b438657d1cee116ba737807ea71d19d6de4b90f799a09c56f0cc6a1b0ff`): 155 of its 178 codes. The 23 left out (fund, metal,
unit and test codes: BOV CHE CHW CLF COU MXV USN UYI UYW XAD XAG XAU XBA XBB XBC XBD XDR XPD XPT XSU XTS XUA XXX) are
excluded by Sentinel's ruling of 6 November (funds, metals, bond-market units, the SDR, test and no-currency codes; not every `X` code
and not the fund flag alone, so XAF XCD XOF XPF XCG ZWG stay). The set is a frozen literal, read from no file at run time;
codes are matched exactly, so lowercase `usd` and ANG, BGN and ZWL, which are not in the 2026-09-17 file, are refused. The derivation is in `gateway/registry.py`. Tools whose sign-in is `shared` or
`api`, and archived tools, are refused. Errors carry a `code`: `unknown_field`, `bad_route`, `route_unavailable`,
`bad_payer`, `bad_tool`, `tool_not_allowed`, `bad_kind`, `bad_value`, `bad_number`, `bad_date`, `bad_currency`,
`bad_text`, `too_long`, `looks_like_secret`, `account_limit`, `already_registered`, `value_limit`, `account_ended`,
`no_such_account`, `rate_limited`.

**Console API** (`/admin/api`, read only, `area=(govern, money)`): `GET /provider-accounts[?status=&tool=&person=&limit=] (`person` = the holder's id: one person's seats, never their individual accounts)` and
`GET /provider-accounts/<id>`. What a console user sees is the record kind's field ceiling intersected with their
areas, then the union across the areas they hold; the ceiling applies to an owner too. **Individual accounts are holder-only:**
the console lists seat accounts only (also with `?tool=`), and an individual account's id answers the same 404 as a missing one
to every console user, the owner included. No list, read or count includes one. The one residual: a govern user trying to delete an admin-added tool that any registry row points at gets 409 `has_provider_accounts`, which shows that someone has declared an account for the tool but not who, the route, how many or when (Sentinel, Low, accepted). Viewer, security, emergency-only
and admin-only users get 403. The console writes nothing here.

**Seat coverage** (same areas, read only): `GET /provider-accounts/coverage?tool=<id>` answers "who is authorised for this
provider, and do they have a seat?" for one tool. It returns `{tool: {id, name, signin}, people: [{person_id, name, department,
access: {state, reason}, seat: null | {id, status, assertion, confirmed: false, created}, coverage}], summary, note}`, where
`coverage` is `authorised_with_seat`, `authorised_without_seat` (the Hub lets them use it, no seat declared) or
`seat_without_access` (an active declared seat, but the Hub does not let them use it). Access is the Hub's own rule
(`entitle.status`: subscription active AND assigned, person active). Only active seat records are read: an individual account
never changes a row, a count or the shape, and no value, label or payer is returned. Missing `tool` → 400 `bad_tool`, unknown
→ 404 `no_such_tool`. It writes nothing (no audit row for a read).

| Fields | holder | govern | money |
|---|---|---|---|
| Individual: every field and value | yes | no | no |
| Seat: id, tool, route, status, created, ended, holder, payer, assertion, confirmed, label | yes | yes | yes |
| Seat: plan, quota_limit, quota_used, period_end | yes | yes | no |
| Seat: credit_balance, monthly_price | yes | no | yes |

Why individual accounts have no console row at all (Sentinel F1): even an id, status and timestamps could be matched with the
audit log's named actor, target and time, and so reveal which tool a person holds personally.

**Audit.** The audit log is readable by every console user, so registry entries are deliberately thin: the actor is the
holder's name (as in every other entry), the action is one of `registered a provider account`, `recorded a provider account
value`, `ended a provider account`, and the target and correlation are `provider_account:<id>`. Before/after hold a status
or a value id and nothing else: no tool, route, kind, payer, label or value, ever. The correlation is not `person:<id>`, so
these entries never appear in a person's Timeline. The general audit semantics are unchanged. **Disclosure:** every console
user can therefore see *that a named person changed a provider-account declaration, and when*; the tool, route, kind and
contents are reachable only through the field-gated registry reads above. The staff Privacy page must say so before this
ships (a separate UI task; the registry stays unreleased until it is done). What remains visible is deliberate: a named
registry change and its time, and, because a seat's id is readable in the console, a `provider_account:<id>` that is *not* a
listed seat id may imply an individual account was changed, but never which tool, route or contents.

**Known legacy note (Low, not a blocker).** The earliest form of v24 (commit 48cc003) had no `CHECK (id > 0)`. On a database
created from it, a direct SQL insert that supplies a negative id can make later automatic-id inserts fail (the guard sees an
auto-assigned id as -1). There is no HTTP path that supplies an id, and no data is lost. No v26 and no production state is
assumed. If a real non-fixture database in that form is ever found, the future additive repair would be an AFTER INSERT abort
on `NEW.id <= 0` plus an `NEW.id > 0` guard on the `no_replace` id check; it is not authorized now.

Not built, by design: any UI, admin write, outbound call, OAuth, sync, webhook, stored secret, sharing, workspace
pointer or company-held account.
